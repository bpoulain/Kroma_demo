Kroma at a glance

Kroma builds a parametric colour system: instead of picking each colour by hand, you set curves (lightness, chroma or saturation) shared by every hue of a category. Changing a curve changes every ramp of that category, and the progression stays consistent from one hue to the next.

Category
Two categories: colored and neutral. Each has its own curves and colour space.
Ramp
One hue in steps, from lightest to darkest (for example blue from 050 to 950).
Step
A position on the ramp. The number of steps (2 to 20) is a system setting; their labels follow from it (1000 ÷ (n + 1) × i, on three digits).
Pure grey
A neutral ramp can be pure grey: it keeps the neutral lightness curve, with no chroma at all (set in the Neutral curves panel).

Two places: Ramps, where you tune and check colours, and Theme, where you name semantic tokens and declare the pairs to check.

Colour spaces and gamut

OKLab is a perceptual colour space proposed by Björn Ottosson in December 2020: an equal distance roughly matches an equal perceived difference. OKLCH is its cylindrical form: L (lightness, 0 to 1), C (chroma, how intense the colour is) and h (hue, in degrees). The oklab() and oklch() functions are part of CSS Color 4.

OKHSL, by the same author (2021), keeps the shape of HSL (hue, saturation, lightness) on top of OKLab: a saturation from 0 to 1 stays inside the sRGB gamut. In Kroma, the same hue value gives the same hue in OKLCH and in OKHSL.

The gamut is the set of colours a screen can show. An OKLCH colour can fall outside sRGB (common screens) or Display P3 (wide-gamut screens). In the Ramps toolbar (Out of gamut), Clip shows the colour brought back into sRGB; Warn shows the original colour and flags those that fall outside.

Whatever this setting, Kroma computes every contrast and exports every hexadecimal on the sRGB fallback: the colour brought back into sRGB. The exported CSS also carries the oklch() value brought into P3, for screens that can show it.

Curves

Each parameter of a category (lightness, then chroma in OKLCH or saturation in OKHSL) follows a curve along the ramp, from the first step to the last. Six modes:

  • linear: an even progression between a minimum and a maximum;
  • parabolic: one peak, useful for chroma, stronger in the middle;
  • bezier: a Bézier curve whose handles you drag; they may leave the frame, values are brought back within bounds when the colour is produced;
  • exponential: a progression that speeds up;
  • easeInOut: slow at both ends, fast in the middle;
  • custom: one value typed for each step.

Primitives and semantic tokens

A primitive is a ramp colour, named by its ramp and step (blue-500, slate-100). A semantic token names an intent (bg-app, text-muted) and points to one primitive in light and one in dark: the dark theme is built this way, token by token, with no hidden computation.

Each token has a description: its intent, and what not to use it for. It is exported with the token, so the tools and agents that read the export read it too.

Contrast: WCAG 2 and APCA

WCAG 2 (a W3C Recommendation; version 2.2 of 12 December 2024) measures a luminance ratio, from 1:1 to 21:1, the same whichever colour comes first. Its success criteria:

  • 1.4.3 Contrast (Minimum), level AA: 4.5:1 for text, 3:1 for large text;
  • 1.4.6 Contrast (Enhanced), level AAA: 7:1, and 4.5:1 for large text;
  • 1.4.11 Non-text Contrast, level AA: 3:1 for user interface components and graphical objects, against adjacent colours.

APCA (Accessible Perceptual Contrast Algorithm) measures an Lc (lightness contrast), from 0 to about 105, which depends on the order: text on background is not background on text. Kroma shows its absolute value. APCA is the candidate method for the future WCAG 3, which is not final: it is neither a W3C standard nor a WCAG 2 criterion.

Kroma’s usage scale

Kroma ranks each contrast by the most demanding usage it allows, on the APCA “Bronze Simple Mode” levels and the WCAG 2 criteria. The scale is fixed: the requirement is declared pair by pair.

Usage APCA WCAG 2
Body text, preferred Lc 90 7:1
Body text Lc 75 4.5:1
Content text Lc 60 4.5:1
Large text, headings Lc 45 3:1
Spot text, solid icon Lc 30 3:1
Discernible non-text (border, divider) Lc 15 —

Reference algorithm and displayed algorithm

The system declares a reference algorithm (APCA, WCAG 2 or both; APCA by default) in its details: it decides each pair’s verdict. The displayed algorithm (toolbar of a ramp’s matrix and of the pairs) only changes the numbers shown.

Contrast pairs

A pair joins a background token, a text (or element) token and the usage it must meet. Kroma checks it in light and in dark, on the sRGB fallback, and gives a verdict by the reference algorithm. The header counts the pairs that pass in both themes.

A failing pair is fixed from its detail: for its text token and its background token, each step of the ramp shows the verdict it would give, and how many other pairs would fail.

Borders

Criterion 1.4.11 asks that a component boundary stand out from what surrounds it. Two pairs can therefore matter for a border: against the component background, and against the container background. When the component has a solid background different from the container, that background often draws the boundary on its own. This is a reading of the criterion, not a rule it states. The default preset declares both; the rebuilt design-system presets keep their source’s choice.

Surface differences: ΔL* and ΔE2000

Two neighbouring surfaces (the app background and a card’s) often need to stand apart without carrying text. No standard sets a threshold for this. On request (the ΔL* · ΔE2000 button of a ramp’s matrix and of the pairs), Kroma can show two measures for information, with no verdict:

  • ΔL*: the lightness difference in CIE Lab, from 0 to 100;
  • ΔE2000 (CIEDE2000, CIE publication 142-2001): the perceived difference between two colours, lightness, chroma and hue included. The Color.js documentation cites 2.3 as the “just noticeable difference” of most ΔE formulas.

Export formats

DTCG 2025.10: the technical reports of the W3C Design Tokens Community Group (28 October 2025), in three modules, Format, Color and Resolver. It is a stable community group report, not a W3C standard. Kroma exports a single .resolver.json file, with the primitives and both contexts (light, dark) written inside. Each colour carries its OKLCH components and its hexadecimal (the sRGB fallback). The io.github.bpoulain.kroma extension carries the whole system: curves, each primitive’s recipe, descriptions and pairs. It is what Kroma trusts when it reopens the file.

CSS: variables, with the sRGB fallback, then the oklch() value brought into P3 inside an @supports and @media (color-gamut: p3) block. Dark theme by choice: prefers-color-scheme media query, .dark class or [data-theme="dark"] attribute.

Importing an existing system

Kroma reads a DTCG file (Tokens Studio included) or CSS variables. The file’s structure proposes the ramps, the values check them; you confirm. Kroma then looks for curves that reproduce these colours: the imported system stays parametric.

The gap between each original colour and its reproduction is measured in ΔE OK × 100 (distance in OKLab, times 100): the largest gap first, then the median, then each colour. A neutral ramp whose colours all have a chroma under 0.005 (a gap of 0.5) is proposed as pure grey.

Presets

Presets show what the curves can do: OKLCH and OKHSL, modes, numbers of steps.

Loading a preset replaces the whole system, after confirmation; “Export first” keeps the current one.
